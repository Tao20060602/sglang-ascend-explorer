# 维护指南

## 最小内容更新

先在 `src/content.js` 找到模块 id，修订职责或契约。需要新增细节时编辑 `src/explanations.js`，避免把同一规则复制到多个位置。

新增子模块需要：

1. 定义对应节点和固定版本源码链接。
2. 将 id 加到父模块的 `children`。
3. 如果模块间有真实的交互，在 `src/relations.js` 对应层级添加关系。并列功能不必强行连成串行流程。
4. 为相关案例调整 A/C/S 分类及传播步骤。
5. `npm test`，并实际查看目标层级和窄屏。

## 模型与优化因素

`src/models.js` 是模型差异的入口：

- `MODELS` 保存 checkpoint / revision、机制、昇腾覆盖说明、专属节点、状态种类与 Attention 关系。
- `modelContext()` 将画像接入同一个图、目录、源码面板和关系表；不要在渲染器里根据模型名另画一套坐标。
- `modelScenario()` 按容量、布局、主 KV 精度、复用四种意图，结合 `stateKind` 与历史读取角色 `readsHistory` 分配影响。状态种类不能根据标题猜测。
- 模型变化时回到全景，避免把旧模型的内部图层带入新模型。分享链接使用 `model`、`scenario`、`kv`、`scope`；不属于该模型的图层退回全景。

新增模型前，核对官方配置的 architecture、层类型、状态布局和真实的 NPU 分支。普通 MHA、潜变量 KV、共享主 KV、Indexer K、递推状态不是可互换的概念。profile 中的父子层级应为无重复归属的树，跨模块交互用关系表示。

`A` 表示此次直接涉及的工作，不等于“必须重写整个模块”；`C` 表示需要核查。可选的图、HiCache、PD 或推测路径只在启用时检查；页面未模拟真实硬件收益。

变更模型数据后，扩充真实浏览器测试：切换后的节点/源码、状态边界、颜色、分享链接、影响路径导航与新图层的实际几何。不要只检查下拉框标题。

## 关系数据

每条关系写明：

- `from`、`to`：该层存在的节点 id。
- `label`：简短而有辨识度的交互名称。
- `payload`：传递的数据、调用或配置内容；双向时分别说明方向。
- `impact`：契约变化会影响什么，哪些条件下才需要修改。
- `kind`：`call`、`data` 或 `config`；配置约束以虚线展示。
- `both`：是否明确需要双向交换。

坐标、端口位置和折线由 ELK 生成，不在内容文件中维护。

## 验证一个理解

从提出的问题出发：

```text
我认为某模块需要改变
  → 哪个接口或资源约束改变了？
  → 谁生产这些数据？谁消费它们？
  → 对应源码、分支条件与固定版本是什么？
  → 是代码修改、配置调节，还是只需要重新验证？
  → 用什么设备验证结果与性能？
```

“需要核对”不能直接写成“必须重写”；“shape 相同”不能直接写成“语义相同”。权重量化与 KV 量化、图捕获与编译、TP/EP/PD 的不同通信场景都应分开记录。

## 上游更新

统一更新 `SOURCE_COMMIT` 后，逐项核对文件、行号和调用分支，不要只替换链接中的 SHA。更新来源说明，并把没有核对的内容标为待验证。

## 发布

这是静态页面，可以放在任意静态服务器。GitHub Pages 使用仓库根目录时，`index.html`、`styles.css`、`src/` 和 `vendor/` 均需存在。

```bash
git add src docs styles.css index.html
git commit -m "Clarify an architecture contract"
git push
```

个人笔记可先写入 `docs/NOTES.md`，核实后再更新图中的结论。
